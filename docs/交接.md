- 这是一次**学习型项目**：完整走一遍「个人开发 → 小规模美国商业化」的流程，学会后做别的产品。实用价值次要（国内有豆包；SayKey 的意义是私密语音输入）。

## 4. 编译和发布（一步一步）

iOS 只能在 macOS 上编译，所以都在 GitHub Actions 上做。详见 [RELEASE.zh-CN.md](RELEASE.zh-CN.md)。

**编译**
1. 打开仓库 Actions → **Build iPhone keyboard for sideloading** → Run workflow → 选你的分支 → Run。
   - 命令行（已装 GitHub CLI `gh`）：`gh workflow run build-ios.yml --repo Yhaijiao/saykey-ios-keyboard --ref <分支名>`
   - 要跑模拟器界面测试就勾选 `simulator_tests`（命令行加 `-f simulator_tests=true`）。默认不跑，省 Mac 时间。
   - **重要版本联动**：每次改版本号时，除了改 `project.yml` 里的 `MARKETING_VERSION` 和 `CURRENT_PROJECT_VERSION`，**还要同步改 `.github/workflows/build-ios.yml` 里打包与 `verify_ipa.py` 校验的版本号**（共 3 处 `0.4.xx`）。
2. PR 不会自动触发编译，要手动跑。只编译约 3–4 分钟 Mac 时间。
3. 记下这次运行的编号（网址里 `/actions/runs/` 后面那串数字）。

**发布**（PR 合并进 `feature/phone-asr`、一批功能都做完以后）
1. 在 `feature/phone-asr` 上编译一次并确认成功。
2. 同一个 workflow 再 Run 一次，在「只发布」一栏（`publish_run_id`）填上一步的运行编号。
   - 命令行：`gh workflow run build-ios.yml --repo Yhaijiao/saykey-ios-keyboard --ref feature/phone-asr -f publish_run_id=<编号>`
3. 它会校验 SHA-256，把 IPA 以 `CapsWriterLab-sideload.ipa` 的名字传到 `saykey-releases` 的 `lab-phone-asr`。
4. 告诉 Jeremy 版本号，他在手机上点更新。

**发布需要的密钥**：仓库 Settings → Secrets and variables → Actions 里的 `RELEASES_TOKEN`（只授权写 `saykey-releases` 的 fine-grained 令牌，不过期）。**绝不要把令牌读取或打印到任何地方。**

**本地测试**
- 服务端（Python）测试：`python -B -m unittest discover -s bridge -p 'test_*.py' -v`

## 7. ⭐ 给 Claude Code 的重点交接：当前卡点与待办（2026-11-24）

### 7.1 ✅ 已解决（v0.4.38 真机确认 2026-11-24）：主 App 没开语音会话时「跳去 SayKey Lab 开启后再自动跳回原 App」

**结论**：iOS 27.2.1 清空了 `_UIRemoteKeyboards` 事件里的来源信息；有效做法是键盘在 `main` 前强开 `+[_UIKeyboardArbiterClient enabled]`，轮询 `automaticSharedArbiterClient.currentClientState` 建“进程号→App”表，点麦克风时用 `_hostProcessIdentifier` 查表，经 `return=` 交给主 App 按 URL scheme 打开（见第 9 条）。Jeremy 确认 v0.4.38 跳回好用。唯一例外：“添加到主屏幕”的网页版 App（如 Antigravity）会打开临时 Safari 页面跳不回去，v0.4.39 对这类宿主改为显示“点左上角◀返回”提示。以下为排查历史。

**以后跳回再坏，先查这里（速查）**：
- 工作原理（v0.4.38 起）：键盘出现后每秒读一次系统“键盘调度员”对象 `_UIKeyboardArbiterClient` 的 `currentClientState`，里面有当前 App 的 Bundle ID 和进程号，记成“进程号→App”对照表（`ios/Keyboard/HostArbiterWatch.swift`）；点麦克风时用键盘自己的 `_hostProcessIdentifier` 查表，经 `capswriterlab://renew?return=<id>` 交给主 App，主 App 开好会话后按 URL scheme 打开那个 App（`ios/App/HostAppReturn.swift`）。前提是 `ios/Shared/KeyboardArbiterActivation.m` 在 `main` 前把 `+[_UIKeyboardArbiterClient enabled]` 强制为 YES。
- 为什么 v0.4.25–v0.4.37 的老办法失效：它监听 `_UIRemoteKeyboards` 的键盘事件，iOS 27.2.1（Jeremy 2026-11-21 升级）把事件里的来源字段全部清空。
- 诊断：Lab 顶部浮动提示里的 `kd:` 末尾是 `A事件n表项h读取次数s读到状态次数`。`n0` 而 `s` 大于 0 = 系统给了状态但不带 App 名（苹果又改了）；`s0` = 连状态对象都没有。
- 例外：网页版桌面 App（Web App 外壳）iOS 无法按 ID 重新打开，豆包也一样，v0.4.39 改为提示点◀。

#### 现象复现步骤
在备忘录（Notes）里使用 SayKey 键盘 → 若主 App（SayKey Lab）当前未开启语音会话（无论是上滑划掉主 App 冷启动，还是在主 App 里点了「关闭本次语音会话」后切回 Notes）→ 在键盘里点麦克风：
- **能正常跳到 SayKey Lab，且语音会话能正常自动开启（60 分钟）**；
- 手机左上角状态栏也正常显示系统级的 **`◀ Notes`** 返回胶囊；
- **但主 App 无法自动跳回 Notes**，停留在 SayKey Lab 页面并显示顶部提示（需手动点左上角 `◀ Notes` 才能回备忘录）。

4. **v0.4.34（build 47, PR #30，当前已发布版本）—— 深层探测 `RTIDocumentTraits` / 场景 ID / 宿主进程名 + 回传 `kd` 探测码**：

5. **v0.4.35（build 48，Claude Code 接手后第一轮）—— 改为监听“真正在更新”的键盘状态对象**：
   - Jeremy 发来 v0.4.34 截图：`[nav:0 kb:0/0 rep:0 kd:w13.pN]`。`kd:w13.pN` = 键盘扩展里只走了 13 个对象、没摸到 `RTIDocumentTraits`，拿到一个 PID 但沙盒不让查进程名。Apple 官方（开发者论坛 DTS）已确认：键盘扩展在 iOS 26.4+ **没有任何办法**知道宿主 App，继续在键盘侧挖没有意义。
   - 关键发现：`kb:0/0` 里第二个 0 表示主 App **从来没收到过一次**键盘状态事件。网上两个独立开发者（dev.to nr666_dev、OpenWhispr PR #2365，iOS 26.5/26.6 实测）证实：宿主 Bundle ID 仍在主 App 进程里的 `_UIRemoteKeyboards.currentState.sourceBundleIdentifier`，冷启动后约 0.65–0.75 秒到达，而且是**瞬时值**，只能用 KVO 接，不能事后去读；但真正收到它的 `_UIRemoteKeyboards` 实例挂在窗口场景上：`UIWindowScene._registeredComponents["_UIKeyboardSceneDelegateSceneComponentKey"]`（UIKeyboardSceneDelegate）→ `containerWindow` → `editingOverlayViewController` → `parentViewController` → `hosting` → `hostingItems[]` → `controllerDelegate`。我们以前只监听类方法 `sharedRemoteKeyboards` 返回的那个对象，在新系统上它不再收到事件 → 这就是回归原因（随 iOS 升级而坏，不是某次代码改坏）。
   - 修改：`ios/App/HostAppReturn.swift` 新增 `attachKeyboardObservers()`，沿上面链路（加上几个备用 getter）找出所有 `_UIRemoteKeyboards` 实例并全部 KVO（`.initial` 立即拿到当前值）；启动、回前台、变活跃时以及跳回等待循环里每 0.5 秒再找一次（该对象可能等主 App 上屏后才创建）。每一步都运行时检查，找不到就安静失败。
   - 诊断码变为 `[nav:x kb:当前/收到过/监听实例数 rep:x kd:...]`。如果 v0.4.35 仍失败：第三个数字是 0 → 链路没找到实例；≥1 但第二个数字是 0 → 实例找到了但没收到事件。

6. **v0.4.36（build 49）—— 键盘状态改为也读底层字段 + 事件计数诊断**：
   - v0.4.35 真机结果：`[nav:0 kb:0/0/1 rep:0 kd:w13.pN]`，即只找到 1 个 `_UIRemoteKeyboards`（就是 `sharedRemoteKeyboards`），窗口场景那条链没找到第二个实例，且从没解析出来源。
   - 代码考古结论：**v0.4.25 → v0.4.28 之间主 App 跳回代码、键盘跳转代码完全没变**（`git diff 99918ac f49537c -- ios/App` 为空，键盘只改了词库/拼音/按键），而 Jeremy 在 v0.4.28 前后就发现坏了 → 已确认是 **iPhone 系统升级**（11-21 升到 iOS 27.2.1）让旧方法失效，不是某次代码改坏。v0.4.25 的“跳回”本身也是靠认出来源 App 再按 URL scheme 打开（外加一个在新系统上已不存在的系统“◀”返回动作），iOS 没有“直接返回上一个 App”的公开办法。
   - 修改：`source(of:)` 在 getter 不存在时直接读 ivar（新系统可能删了 getter，只剩 `_sourceBundleIdentifier` 字段），并扫描状态对象所有名字含 bundle/scene/source/host 的字符串字段。诊断码新增 `ev:事件数/带状态数+标记`（B=有 bundle 字段、S=有 scene 字段、O=字段只含本 App 或系统层）。

8. **v0.4.37 真机诊断结论（2026-11-24，iOS 27.2.1）—— 读取来源 App 这条路已死**：
   - Jeremy 粘贴回来的 3 个状态对象：第 1 个是 `NSNull`，后 2 个是 `_UIKeyboardChangedInformation`，其中 `_sourceBundleIdentifier`、`_hostBundleIdentifier`、`_sourceSceneIdentityString`、`_sourceDisplayIdentifier`、`_applicationIdentifier`、`_bundleIdentifier` 全是 nil，`_hostProcessIdentifier`/`_processIdentifier` 全是 0，`_keyboardOnScreen=false`。即 iOS 27.2.1 发给第三方 App 的键盘事件已**抹掉所有来源信息**。
   - 结论：靠“认出来源 App 再按 URL scheme 打开”的自动跳回（v0.4.18–v0.4.37 所有方案）在 iOS 27.2.1 上无法实现；键盘仲裁开关也无效。v0.4.36 加的 `KeyboardArbiterActivation.m` 无效果，可考虑下次删掉。
   - 豆包在同一手机上仍能跳回，机制未知（可能是键盘内直接录音、无需跳主 App，或别的私有办法）。备选：① 键盘内用隐藏 `WKWebView` + `getUserMedia` 直接录音（anomalyco/hex PR #1999 在 iOS 27.2 实测可用，公开 API），彻底不用跳主 App；② 交互兜底：醒目提示点左上角 ◀，回去后键盘自动开始录音。

9. **v0.4.38（build 51）—— 按 dictus 源码改为轮询仲裁客户端**：
   - 读了 getdictus/dictus-ios 源码（`HostAppResolver.swift`，该项目 issue #567 有 iOS 27.0 真机跳回 Notes 的记录）：他们**不是**监听 `_UIRemoteKeyboards`，而是轮询 `[_UIKeyboardArbiterClient automaticSharedArbiterClient].currentClientState`，读 `sourceBundleIdentifier` + `processIdentifier` 建“进程号→App”表，点麦克风时用 `UIInputViewController` 的 `_hostProcessIdentifier` 查表。键盘出现约 200 ms 后才有值，没有事件，只能轮询。
   - 修改：`HostArbiterWatch.harvest()` 在键盘出现时、0.2/0.6 秒后、每秒、每次文字变化时读一次；点麦克风时再读并查表。主 App 也读同一对象并写进诊断剪贴板（`client:` 一行）。诊断 `kd:` 末尾变为 `A事件n表项h读取次数s读到状态次数`。

### 7.1b 逐句识别润色（v0.4.39，改的是电脑桥接）

Jeremy 要的效果：说一个字上屏一个字；说下一句时上一句已经开始加工润色；全部说完停止时再整体改一遍段落。

- 第一层“每个字上屏”：原有的边说边上屏草稿（sherpa-onnx 流式模型，键盘以带下划线的临时文字显示），没改。
- 第二层“逐句润色”：`bridge/stream.py` 在每次停顿（约 1.2 秒静音）记下断点；`bridge/sentences.py` 的 `SentencePipeline` 把这一句的音频交给电脑上的 Qwen3 准确识别，再走热词 / 去语气词 / Ollama 标点润色，结果替换草稿里那一句。手机收到的 `partial` = 已润色的句子 + 还在识别的句子草稿 + 正在说的这句草稿。手机端代码不用改。
- 第三层“整段修改”：停止后只需要识别最后一小段，把各句的原始识别文字拼起来，整段再过一次热词和润色（`engine.correct_final` → `Polisher.polish(paragraph=True)`）；超过 150 字时提示模型在换话题处分段（单个换行），超时按长度放宽到最多 20 秒。
- 兜底：任何一句识别失败、或停止后 30 秒还没识别完，就按老办法整段重新识别，不会丢字。
- 开关：桥接启动参数加 `--no-sentences` 可关掉逐句，恢复老行为。
- **上线需要更新电脑上的桥接代码并重启桥接**（拉取 `feature/phone-asr` 最新代码后双击 `后台启动语音桥接.cmd`）。
